# Popover
Popovers display contextual information when users click an element or activate it with the keyboard, and can also open when users hover over it. They typically contain more information than tooltips and can include interactive elements.

## Guidelines

#### When to use

- Use popovers for complex information that might overwhelm the main content
- When content needs to include interactive elements
- For non-essential information that requires user interaction to display

#### When not to use

- Don't use popovers for critical information that must be readily available
- Avoid using for simple text-only tooltips
- Don't nest popovers within other popovers

## Usage Notes

Keep popover content concise and ensure every trigger element is focusable so keyboard users can open and dismiss the overlay reliably.

Use `open-on="hover"` for previews, where the popover adds detail about its trigger but nothing depends on it. Keep essential actions reachable by click: touch and keyboard users never hover, and a hover-opened popover closes shortly after the pointer moves away.

#### Manual

Popovers with the `popoverType="manual"` require explicit user interaction to close. This means they won't automatically disappear when clicking outside or pressing Escape. Inside a modal, though, Escape closes the modal, and the popover closes with it.

The `popoverTargetAction` property determines how the trigger button interacts with the popover:
- `show`: Only shows the popover (default)
- `hide`: Only hides the popover
- `toggle`: Alternates between showing and hiding

For manual popovers, using `popoverTargetAction="toggle"` is recommended as it allows users to both open and close the popover using the trigger button.

Learn more about popover target actions in the [MDN Documentation](https://developer.mozilla.org/en-US/docs/Web/API/HTMLButtonElement/popoverTargetAction#showhide_popover_action_with_a_manual_popover).

### Open on hover

Set `open-on="hover"` to also open the popover when the pointer rests on the trigger. It opens after a short delay, so a pointer passing over the trigger doesn't open it, and closes shortly after the pointer leaves both the trigger and the popover, so the pointer can move into the popover to read or select its content.

- A click on the trigger keeps a hover-opened popover open. From then on it closes the way a clicked-open popover does, so with `popover-target-action="toggle"` the next click closes it. With `popover-target-action="hide"`, the click closes it instead.
- Enter or Space on the trigger opens it, as in the default mode, and Tab then moves into it. Focus alone doesn't open it.
- While focus is inside the popover, it stays open after the pointer leaves, and closes once focus leaves too.
- Escape closes a hover-opened popover, `manual` ones included. Once a click keeps a `manual` popover open, it ignores Escape again, like one a click opened.
- On touch screens a tap opens it, as in the default mode.

### Padding

The `padding` prop sets the space around the popover content. It takes `none`, `xs`, `sm` or `md` from the same spacing scale as `pds-box`. Default is `md` (24px). Use `xs` (8px) to match the dropdown menu and other option lists, `sm` (16px) to match the datepicker, and `none` when the content brings its own spacing.

## Technical Notes

- The trigger slot automatically receives `aria-expanded` and `aria-controls` attributes when the component is hydrated. The popover owns them: if anything removes or changes them, such as a DOM morph, it puts its values back. A script that undoes them as soon as they come back (from a `MutationObserver`, say) wins after a few rounds, and the component logs a console warning. Use focusable elements (buttons, chips, avatar with `dropdown="true"`, etc.) so that keyboard users can open the popover with Enter or Space.
- Content is teleported to `document.body` via a portal to ensure it is correctly layered above other UI. The Tab order still treats it as coming right after the trigger: while the popover is open, Tab from the trigger moves to the first control in the content, Tab from the last control moves on to whatever follows the popover, and Shift+Tab goes back the same way. Content with nothing to focus is skipped. One nested case isn't covered: when a popover is the last control in another popover's content, Tab from the end of the inner popover's content goes past whatever follows the outer popover's trigger. Inside an open dialog, such as a `pds-modal`, it goes into the dialog instead, right after the popover, so it shows above the modal and comes next in the Tab order. When the popover sits in another component's slot (such as `pds-input`'s `action` slot) or in a form inside the dialog, the content goes at the end of the dialog instead, so it renders and its buttons don't submit the form. When a form wraps the whole dialog, a submit from inside the open popover (a button, or Enter in a field) is stopped instead. Because the markup is outside the component's DOM tree, associate it with the trigger via `aria-labelledby` or `aria-describedby` when the content needs more context (for example, referencing the trigger text).
- Auto popovers (`popover-type="auto"`) listen for outside clicks and Escape to close the overlay. Escape closes only the popover opened last, so with one popover inside another, the inner one closes first. Inside a modal, the first Escape closes the popover and the next closes the modal. Closing the dialog a popover is in closes the popover too, auto or manual. Manual popovers must expose their own dismissal affordance—include a close button in the content and wire it to `popover.hide()`.
