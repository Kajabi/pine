# Switch

Switches toggle a single setting between on and off, rendered as a sliding thumb inside a track. They work as form-associated inputs whose checked state submits with the surrounding form.

## Guidelines

### When to use
- Use the `Switch` when you need a binary choice in a compact form, like enabling or disabling a feature.
- Ideal for toggling options in settings or preferences.

### When not to use
- Avoid using for actions that require multiple options or a more complex selection (e.g., radio buttons).
- Do not use for situations where the user's choice needs to be explicitly confirmed.

### Accessibility
- The switch's helper message, or its error message while it's invalid, is announced as its description.
- To explain why a switch is disabled, put the reason in `helper-message`. A tooltip around a disabled switch opens on hover only: a disabled switch can't take focus, so people using a keyboard never reach it, and screen readers don't get the tooltip text. See [Disabled with a reason](#disabled-with-a-reason).
  - Tab still skips a disabled switch, as it does any disabled control. Screen readers reach it, with its helper message, when reading through the page. If the reason must be reachable by Tab, keep the switch enabled and explain the problem when it's changed.
- `aria-describedby` on `pds-switch` describes the switch with text elsewhere on the page, such as a card's description beside it. The text it points at is announced first, then the switch's own message. See [Described by text outside it](#described-by-text-outside-it).
  - The ID reference passes to the inner input as the elements it points at, since an ID can't reach inside the shadow DOM. The element must be in the same document as `pds-switch`, or in a shadow root that contains it.
  - The element must exist when the switch renders, when it takes focus, or when the attribute is set. One added or replaced later is picked up the next time the switch is focused. A disabled switch can't take focus, so to change its description, update the referenced element's text rather than replacing the element.
  - This needs ARIA element reflection: Chrome and Edge 135+, Firefox 136+, Safari 16.4+. Older browsers announce the switch's own message only. jsdom, and so React Testing Library, doesn't implement it either, so unit tests there won't see the description.
- Put only non-interactive content in the `label` slot. Buttons and links inside a label are invalid HTML.
- State on the host follows the component's props: the `pds-switch--error` class and `aria-disabled`. It comes back if something removes it, such as a DOM morph, so change it through props. A script that undoes them as soon as they come back (from a `MutationObserver`, say) wins after a few rounds, and the component logs a console warning.

### Label slot

Use the `label` slot when the label needs more than text, such as a `pds-chip`. Clicking the slotted content toggles the switch, and its text becomes the switch's accessible name. Without slotted content, the `label` prop renders as usual.

## Form Integration

- Provide a `name` so the switch contributes a value to `FormData` when checked. Without `unchecked-value`, an unchecked switch is omitted like a native checkbox.
- Set `unchecked-value` when the form needs an explicit off value, such as `"0"` for a Rails boolean. An unchecked switch then submits it under `name`, so you don't need a hidden input beside it. An empty string submits a blank value. A disabled switch submits nothing, whether `disabled` is set as an attribute or a property.
- Use `value` (default `"on"`) to differentiate multiple switches that share the same `name`.
- Combine `checked`, `onPdsSwitchChange`, and state management for controlled React usage, and pair `required`/`invalid` to enforce acknowledgements such as terms of service.
