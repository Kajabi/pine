# Combobox

A combobox is a text input with a dropdown list of options, allowing users to filter and select from a list. It is useful for searchable selects and autocomplete scenarios.

## Guidelines

### When to use
- When users need to select from a long or searchable list of options.
- When you want to allow both typing and selection.
- When you need rich layouts in options or trigger content.

### When not to use
- For simple, short lists (use [Select](/docs/components-select--docs)).
- For multi-select (use checkboxes or a multi-select component).

### Accessibility
- Implements the WAI-ARIA Combobox Pattern for screen reader compatibility.
- Supports full keyboard navigation: Arrow keys, Enter, Escape.
- Input is labelled and controls the listbox.
- Custom layouts maintain proper ARIA attributes and focus management.

## Usage Notes

### Working with Labels

When analyzing designs or screenshots, text that appears above an input field is the input's label, not a separate `pds-text` component. The `label` prop creates text that appears above the input field and integrates properly with the component's styling and accessibility features.

## Modes

The combobox supports two modes:

- **Filtering** (`mode="filter"`): Filters options as you type (default).
- **Select-only** (`mode="select-only"`): Always shows all options, regardless of input value.

Use the `mode` prop to control this behavior.

## Triggers

The combobox supports three trigger types:

- **Input** (`trigger="input"`): Renders a text input (default, for filtering/autocomplete).
- **Button** (`trigger="button"`): Renders a button-like div (for select-only, non-editable comboboxes).
- **Chip** (`trigger="chip"`): Renders a chip component (for select-only, styled as a chip).

Use the `trigger` prop to control this behavior. See [WAI-ARIA Combobox Patterns](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/#examples) for more details.

## Trigger Variants

The button trigger supports the following visual variants, matching Pine button styles:

- **secondary** (default)
- **primary**
- **accent**
- **destructive**

Use the `triggerVariant` prop to control the style.

### Important Notes

- **Value vs. Display Text**: When using the `value` property, provide the option's `value` attribute (e.g., `value="panda"`), not the display text. The combobox will automatically show the corresponding option's text content (e.g., "Panda").
- **Form Integration**: Preselected options work seamlessly with forms and will be included in form submissions.
- **Dynamic Updates**: The `value` property can be updated programmatically to change the selection at runtime.

## Sizing and Positioning

You can control the dropdown's placement, width, and height, as well as the trigger width using the following props:

- `dropdownPlacement`: 'bottom-start' | 'bottom-end' | 'top-start' | 'top-end' (default: 'bottom-start')
- `dropdownMount`: 'host' | 'body' (default: 'host') — also known as an “append to body” pattern; use `body` inside scrollable modals or other `overflow: hidden` containers so the list is not clipped. When `body` is used, the portal mounts inside the nearest `<dialog>` when present (including `pds-modal` / `showModal()`), resolving through slots and shadow roots so the list stays in the top layer; otherwise on `document.body`. Keyboard focus stays on the trigger, or moves to the panel's own search field, so modal focus traps keep working. The mounted dropdown renders in its own shadow root with the combobox's styles, so it needs no global CSS and page CSS can't reach it: customize it with custom properties on `pds-combobox`. Its reading direction, language, theme and custom properties are taken from the combobox when it opens.
- Listbox `id` and `aria-controls` use `${componentId}-listbox` (for example `my-combobox-listbox`), not a shared `pds-combobox-listbox` id. Option row `id` values use `${componentId}-option-${index}` for unique `aria-activedescendant` when multiple comboboxes exist on the page.
- `dropdownWidth`: Any valid CSS width value (default: '236px')
- `triggerWidth`: Any valid CSS width value for both input and button triggers (default: 'fit-content')
- `max-height`: Any valid CSS height value (e.g., '200px', '10rem') to limit dropdown height with scrolling

### Truncate
By default, a long label wraps in the button trigger and in the options. Set `truncate` to keep each one on one line, with an ellipsis where it's cut. It applies to the button trigger's default label (every variant and shape, with or without an icon) and to text option labels, including those with an icon and those inside a group. The input trigger is already one line, so there `truncate` only changes the options. It doesn't change the chip trigger, custom layouts (`trigger-content`, layout and chip options), or group captions and group rows, which still wrap. `truncate` reflects, so the host can shrink below the label's width in a flex row on its own; give it a `trigger-width` for an exact width instead.

The full label stays available:

- The trigger's accessible name and value, and each option's name, are the full label; truncation only changes how it looks.
- When the trigger's or an option's label is cut, hovering it with a pointer shows the full label in a `title`. A label that fits gets no `title`. A `title` doesn't show on keyboard focus or touch, so keyboard and touch users see only the cut text; keep labels that must be read in full short enough to fit. The `title` only shows while the pointer is over the label text itself — hovering an option's icon, chevron or check mark, or the surrounding padding, shows nothing. It's also the browser's own unstyled tooltip, so unlike Pine's other truncation tooltips it doesn't follow the theme.

### Layout Best Practices

When using custom layouts:

1. **Use semantic HTML**: Structure your layout with proper headings and content hierarchy
2. **Include search text**: Add `data-search-text` attribute to layout options for filtering
3. **Maintain accessibility**: Ensure custom content is screen reader accessible
4. **Keep it simple**: Don't overcomplicate layouts - focus on essential information
5. **Test thoroughly**: Verify keyboard navigation and screen reader compatibility

The rules are the same as for group icons: an icon name only, decorative, and hidden from assistive technology. Once an option is chosen, the `button` trigger shows its icon too, or its group's icon when the option has none. The `input` and `chip` triggers don't show option icons.

Option icons suit a list of categories, where the ungrouped options and the groups between them all have icons. With `flyout` and `drill-in`, the groups sit between the options in the array's order. See the `OptionIconsWithGroups` story.

### Grouping the `options` Prop

When options come from the `options` prop, set `group` on each option, and optionally `groupIcon` (the same rules as `data-icon`). Options that share a group render together under one label, where the group first appears, even if the array interleaves groups. The first option in a group that sets `groupIcon` provides the icon. With `group-display="inline"`, options without a group are listed before every group, wherever they appear in the array, so none reads as part of the group above it. With `flyout` and `drill-in`, groups are rows of their own, so options without a group and groups keep the array's order. With `async-url`, each page of results is merged into the groups already shown, so a later page can add options above the end of the list. `groupIcon` is a string icon name in React too, not an imported icon object. See the `OptionGroupsFromOptions` story for interleaved groups rendered together.

```jsx
<PdsCombobox
  componentId="combobox-grouped-options-example"
  label="Action"
  trigger="button"
  mode="select-only"
  options={[
    { id: 'tag-add', text: 'Add a tag', group: 'Tag', groupIcon: 'hashtag' },
    { id: 'tag-remove', text: 'Remove a tag', group: 'Tag' },
    { id: 'email-send', text: 'Send an email', group: 'Email', groupIcon: 'mail' },
  ]}
/>
```

- **Pass `drill-in-back-label` with `flyout` too.** A flyout drills in when there's no room beside the dropdown, and the back row's screen-reader prefix is English by default.
- **Give every group an icon or none.** A mix reads as unfinished.
- **For server-searched lists (`async-url`), prefer `inline`.** Results replace the groups as soon as you type, so a group list adds a step without helping.

- **Use `panel-search` with the `button` and `chip` triggers** once a grouped list is long enough to need searching. The `input` trigger already searches.

#### In server-rendered templates

The `options` prop is JavaScript-only. In ERB or other server-rendered markup, slot `<optgroup>` elements instead, with each group's icon in `data-icon`, and listen for `pdsComboboxChange` in a script. The `name` attribute submits the value with the form.

- `data-icon` takes a Pine icon name only; URLs and other values that aren't a name are dropped.
- Keep labels and values in escaped output (`<%= %>`). The template is page HTML, so unescaped text becomes markup, or breaks out of an attribute, before the combobox reads it. Never pass user-supplied text through `raw` or `html_safe`.

```erb
<pds-combobox
  component-id="automation-action"
  name="automation[action]"
  label="<%= t(".action_label") %>"
  placeholder="<%= t(".action_placeholder") %>"
  trigger="button"
  mode="select-only"
  group-display="flyout"
  panel-search
  search-placeholder="<%= t(".search_actions") %>"
  search-options-label="<%= t(".search_actions") %>"
  drill-in-back-label="<%= t(".back") %>"
  value="<%= @automation.action %>">
  <% @action_groups.each do |group| %>
    <optgroup label="<%= group.label %>" data-icon="<%= group.icon %>">
      <% group.actions.each do |action| %>
        <option value="<%= action.id %>"><%= action.label %></option>
      <% end %>
    </optgroup>
  <% end %>
</pds-combobox>
```

### Flyout Groups

Set `group-display="flyout"` to list the groups instead of every option. Hovering or clicking a group opens its options in a flyout beside the dropdown, and the group holding the current selection is highlighted. The arrow keys move through every option across the groups, opening each option's group as they reach it, while focus stays on the trigger; the group rows themselves are for the pointer. While searching, matching options are listed under their group labels, and search also matches group labels, so typing a group's name finds all of its options.

- Use it when there are many groups and the full list would be long, such as choosing an automation action.
- Groups come from `<optgroup>` elements or the `group` field of `options`. Options under a `<pds-text>` heading are listed ungrouped.
- The flyout is as wide as its options, between `flyout-min-width` (default `280px`) and `flyout-max-width` (default `380px`). It opens on the side with room, and scrolls when a group is taller than the space available.
- Inside a modal, set `dropdown-mount="body"`; the flyout moves with the dropdown.

```jsx
<PdsCombobox
  componentId="combobox-flyout-example"
  label="Action"
  groupDisplay="flyout"
  dropdownMount="body"
  options={[
    { id: 'tag-add', text: 'Add a tag', group: 'Tag', groupIcon: 'hashtag' },
    { id: 'tag-remove', text: 'Remove a tag', group: 'Tag' },
    { id: 'email-send', text: 'Send an email', group: 'Email', groupIcon: 'mail' },
  ]}
/>
```

### Drill-In Groups

Set `group-display="drill-in"` where nothing can open beside the dropdown, such as a side panel. The dropdown lists the groups, and clicking one replaces the list with that group's options and a row back to the groups. `group-display="flyout"` drills in on its own when there is no room for a flyout on either side. Translate the back row's screen-reader prefix with `drill-in-back-label` (default `Back`). ArrowLeft or Escape also steps back to the groups, and so does Backspace with `panel-search`.

Unlike `flyout`, drill-in doesn't shade the group holding the selection, or the row you come back to with the pointer: a shaded row there reads as picked. The selected option shows its check inside its group. A row shades while the pointer is over it, and with the arrow keys the row you're on is shaded and outlined; the first arrow press shows, and announces, where the keys start. After a touch, rows don't shade on hover, since touch browsers keep a tapped row hovered. A `flyout` that drills in for lack of room works the same way.

With `panel-search`, the search field shows only over the groups. Inside a group, the back row takes its place above the divider, since one group's options don't need searching, and typing a character starts a search of the whole list.

```jsx
<PdsCombobox
  componentId="combobox-drill-in-example"
  label="Filter"
  trigger="button"
  mode="select-only"
  groupDisplay="drill-in"
  drillInBackLabel="Back"
  options={[
    { id: 'email-status', text: 'Marketing status', group: 'Email', groupIcon: 'mail' },
    { id: 'email-activity', text: 'Email activity', group: 'Email' },
    { id: 'contact-added', text: 'Was added', group: 'Contact' },
  ]}
/>
```

### Searching From the Panel

The `button` and `chip` triggers can't be typed into. Add `panel-search` to put a search field at the top of the dropdown: it takes focus when the dropdown opens, filters the options as you type (matching group labels too in a grouped display), and arrow keys and Enter pick from the results. Pass translated `search-placeholder` and `search-options-label` strings; both default to English. `panel-search` has no effect on the `input` trigger, which already searches. The typed query is also emitted on `pdsComboboxSearch`, as it is for the `input` trigger; it's untrusted user text, so escape it before rendering it and treat it as untrusted when building a request from it.

With `panel-search`, the trigger is a button that opens the dropdown, and the search field is the combobox. Unlike the other triggers, `panel-search` moves keyboard focus into the dropdown. With `dropdown-mount="body"` inside a `<dialog>` (including `pds-modal`) that's fine, because the dropdown mounts in the dialog. Inside a focus trap that isn't a `<dialog>`, such as a custom side panel, check that the trap allows focus into the portaled dropdown, or use `dropdown-mount="host"`.

```jsx
<PdsCombobox
  componentId="combobox-panel-search-example"
  label="Action"
  trigger="button"
  mode="select-only"
  groupDisplay="flyout"
  panelSearch
  searchPlaceholder="Search actions"
  searchOptionsLabel="Search actions"
  options={actions}
/>
```

### Disabled Options

Disable an option to keep it listed but stop it being chosen, such as an action that needs a plan upgrade. Use `<option disabled>`, `<optgroup disabled>` for a whole group, or `disabled: true` on an `options` entry.

- Disabled options are muted, marked `aria-disabled`, and do nothing when clicked or when Enter or Space is pressed on them.
- The keys and the pointer still reach them, as the WAI-ARIA listbox and tree patterns advise, so screen readers announce them as unavailable instead of hiding them. The dropdown never opens with one highlighted.
- A group whose options are all disabled (among those shown, while searching) is marked disabled too. It still opens, on hover or click, or with Right, Enter or Space, so people can see what it holds. Screen readers announce its row as unavailable even though it opens.
- When the combobox is searchable (the `input` trigger, or `panel-search`), search still finds disabled options.
- A `value` that matches a disabled option still shows as the selection, and, unlike a native `<select>`, is still submitted with the form. Validate the value on the server.
- The combobox reads `disabled` whenever it renders but doesn't watch it, so toggling it on a slotted option while the dropdown is open shows on the next change. Updating the `options` prop re-renders at once.
- **Say why an option is disabled**, for example in `helper-message`, which is read with the field. A disabled option can't explain itself.

### Group Labels Best Practices

When using group labels:

1. **Keep labels concise**: Use short, descriptive labels that clearly categorize the options
2. **Maintain logical grouping**: Group related options together in a way that makes sense to users
3. **Consider filtering behavior**: Group labels are preserved when filtering, but only groups with matching options will be shown
4. **Use consistent styling**: Choose either `<optgroup>` or `<pds-text>` consistently within a single combobox
5. **Test accessibility**: Ensure group labels work well with screen readers and keyboard navigation

### ARIA and Accessibility Considerations

`<optgroup>` and `<pds-text>` group labels are rendered differently in the dropdown:

- **`<optgroup>` elements**: Each optgroup's options sit in a `role="group"` named by its `label`, which assistive technology announces on entering the group, helping users understand the relationship between options and their categories.
- **`<pds-text>` elements**: Serve as visual group headers but are purely presentational. They do not provide semantic grouping information to screen readers.

**Recommendation**: Use `<optgroup>` for groups of options, since it groups them in the markup and works with `data-icon`. Use `<pds-text>` for a heading over options that don't belong to an optgroup.

## Async Data Loading

The combobox supports loading options asynchronously from a server endpoint or through consumer-managed async operations. This is useful for large datasets, search-as-you-type interfaces, or when options need to be fetched from an API.

### Built-in Async Fetching

Use the `asyncUrl` prop to enable automatic async data fetching. The combobox will handle debouncing, loading states, and pagination automatically.

**Key Props:**

- `asyncUrl`: API endpoint URL for fetching options
- `asyncMethod`: HTTP method ('GET' or 'POST', defaults to 'GET')
- `debounce`: Debounce delay in milliseconds (defaults to 300ms)
- `fetchTimeout`: Request timeout in milliseconds (defaults to 30000ms)
- `formatResult`: Optional function to transform API response items into combobox options

**Expected API Response Format:**

```json
{
  "results": [
    { "id": "value1", "text": "Label 1" },
    { "id": "value2", "text": "Label 2" }
  ],
  "totalCount": 100
}
```

**Basic Example:**

<DocCanvas
  mdxSource={{
    webComponent: `<pds-combobox
  component-id="combobox-async-basic"
  label="Search Users"
  placeholder="Type to search..."
  async-url="/api/users"
  debounce="300">
</pds-combobox>`,
    react: `<PdsCombobox
  componentId="combobox-async-basic"
  label="Search Users"
  placeholder="Type to search..."
  asyncUrl="/api/users"
  debounce={300}>
</PdsCombobox>`,
  }}
>

### Custom Result Formatting

Use the `formatResult` function to transform API response items into the expected option format:

```javascript
// Web Component
const combobox = document.querySelector('pds-combobox');
combobox.formatResult = (item) => ({
  id: item.userId,
  text: `${item.firstName} ${item.lastName}`,
});

// React
const formatResult = (item) => ({
  id: item.userId,
  text: `${item.firstName} ${item.lastName}`,
});

<PdsCombobox
  asyncUrl="/api/users"
  formatResult={formatResult}
/>
```

### Pagination Support

The combobox automatically handles infinite scroll pagination when the API response includes a `totalCount` property. As users scroll near the bottom of the dropdown, additional pages are loaded automatically.

The `pdsComboboxLoadOptions` event is emitted when more data is needed, allowing you to monitor pagination requests if needed.

### Consumer-Managed Async

For more control over async operations, you can manage the data fetching yourself using the `options` prop and `pdsComboboxSearch` event.

**Key Props and Events:**

- `options`: Array of option objects to display
- `loading`: Boolean to control loading state
- `pdsComboboxSearch`: Event emitted when user types (debounced)
- `pdsComboboxLoadOptions`: Event emitted when more options are needed (pagination)

**Example:**

```javascript
// Web Component
const combobox = document.querySelector('pds-combobox');
combobox.loading = false;
combobox.options = [];

combobox.addEventListener('pdsComboboxSearch', async (e) => {
  const query = e.detail.query;
  combobox.loading = true;

  const response = await fetch(`/api/search?q=${query}`);
  const data = await response.json();

  combobox.options = data.results;
  combobox.loading = false;
});

// React
const [options, setOptions] = useState([]);
const [loading, setLoading] = useState(false);

const handleSearch = async (e) => {
  const query = e.detail.query;
  setLoading(true);

  const response = await fetch(`/api/search?q=${query}`);
  const data = await response.json();

  setOptions(data.results);
  setLoading(false);
};

<PdsCombobox
  options={options}
  loading={loading}
  onPdsComboboxSearch={handleSearch}
/>
```

### Best Practices

When using async data loading:

1. **Set appropriate debounce**: Use 300-500ms to balance responsiveness with server load
2. **Handle errors gracefully**: Show meaningful error messages in the empty slot
3. **Provide loading feedback**: Always indicate when data is being fetched
4. **Consider pagination**: For large datasets, ensure your API supports pagination
5. **Test timeout behavior**: Set `fetchTimeout` based on your API's typical response time
6. **Validate formatResult**: Ensure the function always returns objects with `id` and `text` properties

## Programmatic Clear

Call the `clear()` method on the element to return the combobox to its empty state. It resets the selected option, the trigger text, and the value submitted with the form, then emits `pdsComboboxChange` with an empty `value` (only when something was actually selected or typed).

Emptying the input text does **not** clear the selection. In `mode="filter"` the text is a filter over the option list, so the committed value persists until an option is chosen or `clear()` is called. Use `clear()` whenever a "reset" affordance needs to genuinely empty the control.

## Form Integration

`pds-combobox` is a <pds-link href="https://developer.mozilla.org/en-US/docs/Web/API/ElementInternals/formAssociated" external>form-associated custom element</pds-link>. This means the component participates in `<form>` submission just like native `<select>` / `<input>` controls.

- Provide a `name` attribute so the selected value is included in `FormData`. Without `name`, the control is ignored during submission.
- The submitted value always matches the option's `value` attribute, even when a custom layout/chip trigger is used.
- `mode="filter"` behaves like an `<input>` plus `<datalist>`: users can type new text, but the submitted value will still be one of the predefined options.
- `mode="select-only"` works closer to a `<select>`: typing is disabled for button/chip triggers, and only explicit option values can be submitted.
- Update the `value` prop to control the selection from a parent component (React state, framework store, etc.). The component automatically syncs the input text/trigger label to match the selected option.
- Call [`clear()`](#programmatic-clear) to reset the submitted value. Emptying the input text only filters the option list and leaves the committed value in place.
