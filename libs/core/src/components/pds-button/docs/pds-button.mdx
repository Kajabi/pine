# Button

A button is an interactive element that can be clicked to perform various actions such as triggering an event, submitting data, or navigating to a different location.

## Guidelines

### When to use

- Communicating an action that will occur (e.g. saving a page).
- Triggering or enabling an action, such as submitting requested information (e.g. forms).
- Progressing or regressing a user through a step in a flow (e.g. modals).
- A call-to-action that navigates and needs button styling, such as "Create a product". Set `href`, and `pds-button` renders a link (see [Button Link](#button-link)).

### When not to use
- When space is limited consider an IconButton.
- Navigating without `href`. A button without `href` performs an action on the current page or submits a form.
- A link in running text. Use `pds-link`.

### Accessibility

- Write text that says what the button does, such as "Delete account". On an `icon-only` button the text is visually hidden, but screen readers still read it as the button's name.
- To name an icon-only button without slot text, set `aria-label` on `pds-button` (see [Icon Only](#icon-only)).
- An `aria-label` replaces the slot text as the button's name, so start it with the visible text (e.g. "Edit profile" on a button that shows "Edit"). People using voice control say the words they see.
- Use `aria-pressed` for a button that toggles on and off, and `aria-current` for a link to the current page or step. A link never gets `aria-pressed`, which ARIA allows only on buttons.
- Use `aria-describedby` to add a hint from text elsewhere on the page, such as what the button will do or why it isn't available yet. The visible text stays the name.
- Prefer `aria-label` over `aria-labelledby`. Browsers name the button from `aria-labelledby`, but axe-core reports two violations for it on `pds-button` (see [Technical notes](#technical-notes)).
- A disabled button can't take focus, so people moving through the page with the keyboard skip it, and its `aria-describedby` hint never reaches them. Screen readers still list it when reading the page, as unavailable. Show the reason it's disabled as visible text next to the button.

### Disclosure

Disclosure button variant, intended to be used as a trigger to show or hide content elsewhere on the page.

As the `trigger` slot of a `pds-dropdown-menu` or `pds-popover`, the button's `aria-expanded` is set for you. On a standalone disclosure, set `aria-expanded` and `aria-controls` on `pds-button` yourself, and update `aria-expanded` when the content opens or closes. Clicking the button doesn't change it, so the copied markup below needs your own toggle.

> **Note:** Icon cannot be customized.

<DocCanvas
  mdxSource={{
    react: `
function DisclosureExample() {
  const [open, setOpen] = useState(false);

  return (
    <>
      <PdsButton variant="disclosure" aria-expanded={open ? 'true' : 'false'} aria-controls="disclosure-details" onClick={() => setOpen(!open)}>Disclosure</PdsButton>
      <PdsButton variant="disclosure" disabled>Disabled</PdsButton>
      <div id="disclosure-details" hidden={!open}>Content the disclosure button shows and hides.</div>
    </>
  );
}`,
    webComponent: `
    <pds-button variant="disclosure" aria-expanded="false" aria-controls="disclosure-details">Disclosure</pds-button>
    <pds-button variant="disclosure" disabled>Disabled</pds-button>
    <div id="disclosure-details" hidden>Content the disclosure button shows and hides.</div>
    `
}}>
  <pds-button variant="disclosure" aria-expanded="false" aria-controls="disclosure-details">Disclosure</pds-button>

### Button Link

The button link variant allows a `pds-button` to function as a link. By providing an `href` attribute, the button will render as an anchor (`<a>`) element while maintaining the visual appearance of a button. This is useful for creating call-to-action buttons that navigate to external resources or different parts of your application.

> ***Note:*** When using the `href` attribute, button-specific props such as `type`, `name`, and `value` will be ignored. The component will maintain the same visual appearance but function as a link. `loading` shows the spinner and blocks navigation. `disabled` removes the link's `href`, so it can't be followed or reached with the Tab key.

    <PdsButton variant="secondary" href="/community">Join community</PdsButton>

    webComponent: `
    <pds-button variant="primary" href="/products/new">Create a product</pds-button>
    <pds-button variant="secondary" href="/community">Join community</pds-button>

### Type

The type prop allows a `pds-button` to set a [button type attribute](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button#attr-type).

> ***Note:*** The `type` prop does not apply to buttons with an `href` attribute. When an `href` is provided, the button will render as an anchor (`<a>`) element, and the types will be ignored.

- `button` (default): does nothing on its own, even inside a form. Listen for `pdsClick` to run your action.
- `submit`: submits the form the button is in.
- `reset`: resets the form the button is in. [As noted on MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button#attr-type), this behavior tends to annoy users.

In a form, pressing Enter in an `<input>`, `pds-input`, `pds-select`, `pds-checkbox`, `pds-radio` or `pds-switch` clicks the form's first enabled submit button when that button is a `pds-button`.

The `name` and `value` props aren't included in the submitted form data. The form is submitted through a hidden button that carries only the `type`, so the server can't tell which `pds-button` submitted it.

See the [Forms guide](/docs/guides-forms--docs) for building forms with Pine components.

## Technical notes

`pds-button` copies `aria-current`, `aria-expanded`, `aria-haspopup`, `aria-label` and `aria-pressed` from the `pds-button` element to the `<button>` inside it (or `<a>` when `href` is set), and updates them when they change.

The three ID-reference attributes, `aria-controls`, `aria-describedby` and `aria-labelledby`, can't be copied, since an ID can't reach inside the shadow DOM. They pass to the inner element as the elements they point at instead:

- The element must be in the same document as `pds-button`, or in a shadow root that contains it. If an ID repeats, the closest root wins.
- The element must exist when the button renders, when it takes focus, or when the attribute is set. One added or replaced later is picked up the next time the button is focused.
- A disabled button can't take focus, so that fallback never runs for one. An element replaced while the button stays disabled isn't picked up until the button renders again, such as when it's enabled or the attribute is set again. To change a disabled button's description, update the referenced element's text rather than replacing the element.
- This needs ARIA element reflection: Chrome and Edge 135+, Firefox 136+, Safari 16.4+. Older browsers ignore these three attributes. jsdom, and so React Testing Library, doesn't implement it either, so unit tests there won't see the description or name.
- What doesn't work: an ID inside another component's shadow DOM, such as `<pds-button aria-describedby="help">` pointing at a `#help` rendered inside a `pds-modal`'s own markup rather than in your page.

`aria-labelledby` replaces both the slot text and any `aria-label` as the button's name. axe-core reports two violations on a button named this way: `aria-prohibited-attr`, because the attribute stays on `pds-button`, which has no role, and ARIA doesn't allow naming an element without one; and `button-name`, because axe-core reads ID references only as attributes and misses the name browsers and screen readers get.
