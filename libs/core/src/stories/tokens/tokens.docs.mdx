# Tokens

Design tokens are Pine's named values for color, spacing, type, radius, shadows and stacking order. Each one is a CSS custom property that starts with `--pine-`, such as `--pine-color-text` or `--pine-dimension-md`. They come from the `@kajabi-ui/styles` package and load with the Pine stylesheet, `pine-core.css`, so any page that loads that stylesheet can use them without another import.

Tokens come in three tiers:

- **Core** tokens are raw values, such as `--pine-color-grey-900` (#343332) or `--pine-dimension-100` (8px). They keep the same value in every theme.
- **Semantic** tokens are named for a job, such as `--pine-color-text` or `--pine-color-background-container`. They point at core tokens, and the color ones switch in dark mode. Use these in your own styles.
- **Component** tokens belong to one component, such as `--pine-chip-color-accent`. Pine defines them inside the component that uses them.

## Choosing tokens

Start from the job a style does, then pick the semantic token for that job. Use a core token only when no semantic token fits, and expect it to keep its light-mode value in dark mode.

Don't use `--pine-color-text-tertiary` or `--pine-color-text-subtle` for body text or labels. On a white container they reach 3.9 : 1 and 2.8 : 1, below the 4.5 : 1 that WCAG AA asks for. `--pine-color-text-placeholder` is also 3.9 : 1, so put anything people need in the label or helper text, not the placeholder.

On `--pine-color-background-app` every light-mode ratio drops a little: `--pine-color-text-muted` is 5.1 : 1 and `--pine-color-text-tertiary` is 3.7 : 1. In dark mode every token in this table reaches at least 6.5 : 1 on both the container and app backgrounds.

## Dark mode

Pine switches to dark mode on any element with `data-theme="dark"` and everything inside it. Set it on `<html>` to theme the whole page. Pine doesn't follow the operating system's setting (`prefers-color-scheme`) on its own.

Pine doesn't set `color-scheme` either, so the browser keeps its light scheme for the parts it draws itself, such as scrollbars and the option list of `pds-select`. Set `color-scheme: dark` on the same elements:

```css
[data-theme="dark"] {
  color-scheme: dark;
}
```

`color-scheme` is inherited, including into shadow roots. Matching the attribute also covers the datepicker's calendar, which moves into `<body>` or the nearest `<dialog>` and copies the nearest `data-theme`.

These tokens switch:

- Semantic color tokens, such as `--pine-color-text`, `--pine-color-background-container` and `--pine-color-border`
- The border shorthand `--pine-border`
- The focus outlines `--pine-outline-focus` and `--pine-outline-focus-danger`

These stay the same:

- Core tokens, such as `--pine-color-grey-900` and `--pine-color-white`
- Hex, `rgb()` and other literal colors
- Every other token: shadows, spacing, type, radius, z-index and motion

A core token keeps its light value in dark mode:

```css
/* Don't: core token, stays white in dark mode */
.card {
  background-color: var(--pine-color-white);
}
```

A semantic token switches with the theme:

```css
/* Do: semantic token, turns black in dark mode */
.card {
  background-color: var(--pine-color-background-container);
}
```

A custom property resolves on the element that declares it. If you build your own property from a semantic token on `:root` and set `data-theme` on an element further down, your property keeps its light value inside that element. Declare it on the element that uses it instead:

```css
/* Don't: resolved on :root, stays light inside a dark section */
:root {
  --card-background: var(--pine-color-background-container);
}

/* Do: resolved on the card, follows the nearest data-theme */
.card {
  --card-background: var(--pine-color-background-container);
  background-color: var(--card-background);
}
```

Setting `data-theme` on `<html>` avoids this, because `:root` is then dark too.

Pine components that style themselves with semantic tokens follow the theme in every browser. Dark-mode support is still rolling out one component at a time, and a few dark-mode styles use `:host-context()`, which only Chromium-based browsers support. In Firefox and Safari these keep their light-mode look inside a dark theme:

- `pds-alert` and `pds-chip` colors
- The error-state fill of `pds-input`, `pds-select`, `pds-textarea` and `pds-combobox`
- The panel border of `pds-dropdown-menu` and `pds-datepicker`, and the datepicker's native select menus when `color-scheme` isn't set

The semantic Color and Borders pages list each token's light and dark values.

## Naming

Naming is hard, especially for design tokens. Our chosen naming convention aims to align closely with industry standards. It is meant to be as generic or granular as needed from core tokens down to component-level tokens.

Overall, we follow this convention:

namespace-base-context-modifier

1. **Namespace:** Also referred to as the prefix, it refers to the name of the design system and/or component. The design system name is included automatically as tokens are transformed through Style Dictionary. This is important to include as it prevents conflicts with other custom properties with similar naming conventions that could become available across the product. The name of the component should only be used for component-level tokens.
2. **Base:** The main body of the token, highlighting the category and/or property defined such as color, border, or font-size. These will primarily follow the main categories listed in Tokens Studio.
3. **Context (optional):** Describes _where_ and _how_ the token will be used. These are important designators to separate core from semantic and component tokens. This includes contexts such as background or sentiment.
4. **Modifier (optional):** Refers to any modifiers on the component to call out variants, states, scales, or themes such as hover, primary, 100, or disabled.

### Examples

- `--pine-color-mercury-500` (core): namespace `pine`, base `color-mercury`, modifier `500`
- `--pine-chip-color-accent` (component): namespace `pine-chip`, base `color`, modifier `accent`
- `--pine-color-background-container-hover` (semantic): namespace `pine`, base `color`, context `background-container`, modifier `hover`

## Technical notes

### How tokens are built

Tokens are maintained in the <pds-link href="https://github.com/Kajabi/ds-tokens" external>ds-tokens</pds-link> repository with Tokens Studio. Once a Tokens Studio change merges there, <pds-link href="https://amzn.github.io/style-dictionary/#/README" external>Style Dictionary</pds-link>, a standard tool for exporting one token source to many formats and themes, converts the tokens to CSS custom properties, which ship in the `@kajabi-ui/styles` package. Pine's build bundles that CSS into `pine-core.css`.

In the token source, each tier looks like this:

```
color.purple.500: #6B62F2;              /* core */
color.text.@: {color.grey.900}          /* semantic */
chip.color.accent: {color.purple.100};  /* component */
```

The `@` key is the base value of its group, so `color.text.@` becomes `--pine-color-text`.

### Why tiers work

Tiers let one change reach every component. Suppose the card, table and box backgrounds need to change from `color.white` to `color.grey.100`.

When each component points at a core token, each one has to be edited separately:

```css
/* Don't: core tokens, so every component needs its own edit */
/* Card */
background-color: var(--pine-color-white);
/* Table */
background-color: var(--pine-color-white);
/* Box */
background-color: var(--pine-color-white);
```

When they share a semantic token, changing that token's reference updates all of them:

```css
/* Do: one semantic token, one change */
/* Card */
background-color: var(--pine-color-background-container);
/* Table */
background-color: var(--pine-color-background-container);
/* Box */
background-color: var(--pine-color-background-container);
```

The more components share a token, the more a single change saves, whether it's a container color, a brand color or a theme's text colors.

### Token scale

Within Pine, we use a simple scale to handle variations within categories such as dimensions and font sizes. This numbered scale works proportionally off the base value, which is denoted with a `100` modifier.

For example, our base dimension token, 8px, is written as:

`--pine-dimension-100`

An easy method to calculate new tokens is represented by this formula:

`(desired value * 100) / base value`

Let's say we'd like to add a new dimension token for 72px. We can do:

`(72*100)/8`

…which would give us 900. Our final new token would be:

`--pine-dimension-900: 72px` (hypothetical: Pine doesn't ship this token)

While this does free us from using the "t-shirt sizing" scale for core tokens and the headache that comes with adding new values, "t-shirt sizing" is still used for some of our semantic tokens. Contextually, it makes sense as we are consciously dictating what our scale will be with semantic tokens.

### Dimension tokens

With the release of Tokens Studio version 2.0, the Tokens Studio team has decided to adopt `dimension` as a token category, recommended by the W3C Design Tokens Community Group (DTCG), to match the CSS data type of `<dimension>`. <pds-link href="https://docs.tokens.studio/token-types/token-type-dimension" external>Dimension tokens</pds-link>, like their CSS data type counterparts, are numbers followed by units. They are intended to cover the now-deprecated Tokens Studio categories of:

- Space/Spacing
- Size
- Border Radius
- Border Width
- Background Blur
- X and Y position

`dimension` is a token-authoring category: in the token source, radius and border width values are dimension tokens. In CSS, use the radius, stroke width and spacing tokens described under Choosing tokens.
