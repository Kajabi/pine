# Event Handling
Pine tries to adhere to the browser standards whenever possible. However, with Web Components there are events that are a result of a direct user
interaction, like `click`, `focus` that bubble just fine from inside a Web Component's shadow DOM into the light DOM. But then we have others,
like `change` event, that don't. The difference between those events is that the former are defined as
<pds-link href="https://developer.mozilla.org/en-US/docs/Web/API/Event/composed" external>composed events</pds-link>, while the latter are not.


We also try to dispatch non-composed events by manually creating them on Web Component's host elements, but they do not behave 1:1 like their native
equivalents. This results in unexpected behavior. Similar to React "swallowing" `change` events that are created in such a way and event handlers set with
the `onChange` prop not being invoked.

Due to that, our components dispatch custom events that are named like the native events they are meant to replace, but prefixed with "pds". So form components
like `pds-checkbox`, for example, dispatch an `pdsCheckboxChange` event. Which custom events are available can be found in the "Events" section of each component's
properties table.

## Event Patterns

- **Composition**: All Pine custom events are composed and bubble so you can listen on ancestor elements or `document`.
- **Detail payload**: The `detail` type varies by event: a boolean (`pdsRadioChange`), the native event (`pdsSwitchChange`, `pdsSelectChange`), an object (`pdsTableSort`), or nothing (`pdsAlertDismissClick`). Check the Events table in each component's docs for the exact payload.
- **Preventing defaults**: `pds-table` sorts and syncs its selection from listeners on its own element, so `event.preventDefault()` on `pdsTableSort`, `pdsTableSelectAll` or `pdsTableRowSelected` only stops it when your listener runs first. Listen in the capture phase (`document.addEventListener('pdsTableSort', handler, { capture: true })`), or on the element that emits the event: `pds-table-head-cell` for sorting, `pds-table-head` for select all, `pds-table-row` for row selection. In React, that means `onPdsTableSort` and the others go on those components, not on `PdsTable`. A listener on `pds-table` or `document` without `capture` runs after the table has already acted. Canceling `pdsTableSort` stops only the row reorder: the head cell has already flipped its direction, cleared the other columns' arrows and shown its own. That fits server-side sorting, where you render the rows in that order yourself. If you reject the sort instead, put the arrows back with the head cells' `setActiveSort()` and `clearActiveSort()` methods. Other `pds` events report what happened, and `preventDefault()` has no effect on them.
- **Handled keystrokes**: `pds-modal`, `pds-popover` and `pds-dropdown-menu` ignore an Escape or Tab `keydown` that is already `defaultPrevented` when it reaches them, and `pds-multiselect` does the same for Escape. Modal and popover act on the key after it bubbles up, so a control inside that handles it on its own element first stops the overlay from also closing on Escape or moving focus on Tab. Dropdown menu and multiselect act in `document`'s capture phase, before any element inside sees the key.

## Examples

These examples show you how to use the custom "pds"-prefixed events with Vanilla JS and React.

### Vanilla JS

```html
<pds-checkbox component-id="example" />

<script>
const handleChange = () => {
  console.log('changed!')
}

document.getElementById("example").addEventListener('pdsCheckboxChange', handleChange)
</script>
```

## React

```javascript
const MyApp = () => {
  const handleChange = React.useCallback(() => {
    console.log('changed!')
  }, [])

  return <PdsCheckbox onPdsCheckboxChange={handleChange} />
}
```
