# Accessibility

Pine targets **WCAG 2.1 Level AA** compliance across all components. This guide covers the patterns, attributes, and testing approaches that help you build accessible experiences with Pine.

Most component docs also include a dedicated **Accessibility** section with component-specific guidance.

> **Tip:** Use the **Accessibility** tab in Storybook's bottom panel (powered by `@storybook/addon-a11y`) to run automated checks against any live story.

---

## Keyboard Navigation

Users who rely on keyboard navigation must be able to reach and operate every interactive element.

**Core principles:**
- Interactive elements must be reachable via `Tab` and `Shift+Tab`
- Do not remove or override `tabIndex` unless you have a deliberate focus management strategy
- Custom interactive elements (e.g. `pds-button`, `pds-checkbox`, `pds-switch`) manage keyboard interaction internally — do not suppress their default behavior
- Keep a control enabled when people need to find it, and explain why its action can't run when they use it. `pds-button` doesn't support `aria-disabled`: one set on it isn't passed to its inner `<button>`, and the button still clicks and submits.

### Overlay focus

Each Pine overlay handles focus on its own. Don't move focus out of an open modal or a `modal` drawer from your code, because the page behind it is inert. The component docs describe each one in full: <pds-link href="../?path=/docs/components-modal--docs">Modal</pds-link>, <pds-link href="../?path=/docs/components-drawer--docs">Drawer</pds-link>, <pds-link href="../?path=/docs/components-popover--docs">Popover</pds-link>, <pds-link href="../?path=/docs/components-dropdown-menu--docs">Dropdown Menu</pds-link>, <pds-link href="../?path=/docs/components-tooltip--docs">Tooltip</pds-link> and <pds-link href="../?path=/docs/components-toast--docs">Toast</pds-link>.

- **`pds-modal`** moves focus to its first control when it opens and keeps Tab inside. Escape closes it, and focus returns to the control that had it before the modal opened.
- **`pds-modal` with `disable-top-layer`** moves focus to its first control unless `disable-initial-focus` is set, and lets Tab move between the modal and the page. Escape closes it. Focus returns to the control that opened it only if focus was inside the modal.
- **`pds-drawer` with `modal`** moves focus to its first control and keeps Tab inside. Escape closes it, and focus returns to the control that had it before the drawer opened.
- **`pds-drawer`** moves focus to its first control unless `initial-focus="none"` is set, and lets Tab move between the drawer and the page. Escape closes it from anywhere on the page. Focus returns to the control that opened it only if focus was inside the drawer.
- **`pds-popover`** leaves focus on the trigger. Tab from the trigger moves into the content, and Tab from its last control moves on to whatever follows the popover. Escape closes it unless `popover-type="manual"` is set, and moves focus from the content back to the trigger.
- **`pds-dropdown-menu`** leaves focus on the trigger. Tab or Down Arrow moves to the first item, and Tab past the last item closes the menu. Escape closes it and returns focus to the trigger.
- **`pds-tooltip`** opens when its trigger takes focus and never takes focus itself. It closes when focus leaves the trigger. Escape doesn't close it.
- **`pds-toast`** never takes focus, and Escape doesn't close it. Its message is in a `role="alert"` region.

## ARIA Patterns

### Labels

Prefer visible labels. Give a form control a `label` and a `component-id`: the `component-id` connects the label to the field, and without it the field has no accessible name.

<DocCanvas
  mdxSource={{
    webComponent: `<pds-input component-id="email-address" label="Email address" name="email"></pds-input>`,
    react: `
import { PdsInput } from '@pine-ds/react';

<PdsInput componentId="email-address" label="Email address" name="email" />`
  }}>
  <pds-input component-id="email-address" label="Email address" name="email"></pds-input>
</DocCanvas>

When the design has no room for a visible label, keep `label` and add `hide-label`. The label is hidden on screen, and screen readers still read it as the field's name.

<DocCanvas
  mdxSource={{
    webComponent: `<pds-input component-id="order-search" label="Search orders" hide-label name="q"></pds-input>`,
    react: `
import { PdsInput } from '@pine-ds/react';

<PdsInput componentId="order-search" label="Search orders" hideLabel name="q" />`
  }}>
  <pds-input component-id="order-search" label="Search orders" hide-label name="q"></pds-input>
</DocCanvas>

`aria-labelledby` doesn't name `pds-input`, `pds-textarea`, `pds-select`, `pds-checkbox`, `pds-switch`, `pds-radio`, `pds-combobox`, `pds-multiselect` or `pds-datepicker`: the field inside is left with no accessible name, or only its placeholder. Name them with `label`, and add `hide-label` when it shouldn't show.

Name an icon-only button with `aria-label` on `pds-button`, which passes it to its inner `<button>`. Text in the default slot also names it, because `icon-only` hides the text on screen but not from screen readers.

<DocCanvas
  mdxSource={{
    webComponent: `
<pds-button icon-only aria-label="Close dialog">
  <pds-icon slot="start" name="remove" aria-hidden="true"></pds-icon>
</pds-button>`,
    react: `
import { PdsButton, PdsIcon } from '@pine-ds/react';
import { remove } from '@pine-ds/icons/icons';

<PdsButton iconOnly aria-label="Close dialog">
  <PdsIcon slot="start" icon={remove} aria-hidden="true" />
</PdsButton>`
  }}>
  <pds-button icon-only aria-label="Close dialog">
    <pds-icon slot="start" name="remove" aria-hidden="true"></pds-icon>
  </pds-button>
</DocCanvas>

### Decorative Icons

Mark a decorative icon with `aria-hidden="true"` so assistive technologies skip it.

<DocCanvas
  mdxSource={{
    webComponent: `<pds-icon name="star" aria-hidden="true"></pds-icon>`,
    react: `
import { PdsIcon } from '@pine-ds/react';
import { star } from '@pine-ds/icons/icons';

<PdsIcon icon={star} aria-hidden="true" />`
  }}>
  <pds-icon name="star" aria-hidden="true"></pds-icon>
</DocCanvas>

When an icon conveys meaning with no adjacent label, provide an `aria-label` on the parent interactive element instead (see icon-only button example above).

### Landmark Roles

Give each page one `<header>`, one `<main>` and one `<footer>`, and a `<nav>` with an `aria-label` for each navigation area, so screen reader users can jump between regions. These elements carry their landmark roles already, so they don't need `role` attributes.

```html
<header>…</header>
<nav aria-label="Main">…</nav>
<main>…</main>
<footer>…</footer>
```

### Live Regions

Use a live region to announce content that changes without moving focus, such as loaded results or a validation summary. Screen readers read what you put inside an `aria-live` element.

```html
<div aria-live="polite" aria-atomic="true">
  <!-- Content injected here is announced by screen readers -->
</div>
```

Use `aria-live="assertive"` only for critical errors that must interrupt the user immediately.

## Color and Contrast

WCAG 2.1 AA sets these minimum contrast ratios.

  <pds-table-body>
    <pds-table-row>
      <pds-table-cell>Normal text (&lt; 18pt)</pds-table-cell>
      <pds-table-cell>4.5 : 1</pds-table-cell>
    </pds-table-row>
    <pds-table-row>
      <pds-table-cell>Large text (≥ 18pt or ≥ 14pt bold)</pds-table-cell>
      <pds-table-cell>3 : 1</pds-table-cell>
    </pds-table-row>
    <pds-table-row>
      <pds-table-cell>UI components and focus indicators</pds-table-cell>
      <pds-table-cell>3 : 1</pds-table-cell>
    </pds-table-row>
  </pds-table-body>

Do not use raw hex values or core tokens for text and UI colors in application code. Reference semantic tokens (e.g. `--pine-color-text`) so that contrast is maintained across themes.

See <pds-link href="../?path=/docs/design-tokens-tokens--docs">Tokens</pds-link> for each text token's contrast and when to use it. Pine's <pds-link href="../?path=/docs/design-tokens-color-linting--docs">Color Linting</pds-link> rules check only Pine's own component styles; they don't run on your app.

### Dark mode

Set `data-theme="dark"` on `<html>` to turn on dark mode. Semantic color tokens switch with the theme, but core tokens such as `--pine-color-grey-900` and literal colors such as hex values keep their light-mode value, so check contrast in both themes. The Dark mode section of <pds-link href="../?path=/docs/design-tokens-tokens--docs">Tokens</pds-link> lists which tokens switch.

A few component dark-mode styles use the CSS `:host-context()` selector, which only Chromium-based browsers support. In Firefox and Safari, these keep their light-mode look in dark mode: `pds-alert` and `pds-chip` colors, the error-state colors of `pds-input`, `pds-select`, `pds-textarea` and `pds-combobox`, the panel border of `pds-dropdown-menu` and of the `pds-datepicker` calendar, and the calendar's month, year and time menus. `pds-select` keeps its light error fill in every browser when `invalid` is set without an `error-message`.

## Focus Management

Move focus programmatically when the user's context changes. Pine's overlays move focus on their own (see Overlay focus above), so these cases are yours.

    <pds-table-head-cell>Where to move focus</pds-table-head-cell>
  </pds-table-head>
  <pds-table-body>
    <pds-table-row>
      <pds-table-cell>A submit fails</pds-table-cell>
      <pds-table-cell>The error summary: a <code>pds-alert</code> with <code>tabindex="-1"</code> above the form</pds-table-cell>

    <pds-table-row>
      <pds-table-cell>Route / page change (SPA)</pds-table-cell>

    </pds-table-row>
  </pds-table-body>

For custom focus movement, call `focus()` on the target. An element that isn't focusable on its own, such as a heading, needs `tabindex="-1"` first.

```js
document.querySelector('#my-target').focus();
```

## Forms

These patterns cover form accessibility. See <pds-link href="../?path=/docs/guides-forms--docs">Using Pine Form Components</pds-link> for full form examples and the validation rules.

**Always pair inputs with labels** using the `label` prop and a `component-id`, as in the Labels examples above. Never use `placeholder` as a substitute.

**Inline validation:** set `invalid` and `error-message` on the field in response to user input, and leave focus where it is.

<DocCanvas
  mdxSource={{
    webComponent: `<pds-input component-id="signup-email" label="Email" invalid error-message="Enter an email address, like name@example.com." name="email"></pds-input>`,
    react: `
import { PdsInput } from '@pine-ds/react';

<PdsInput componentId="signup-email" label="Email" invalid errorMessage="Enter an email address, like name@example.com." name="email" />`
  }}>
  <pds-input component-id="signup-email" label="Email" invalid error-message="Enter an email address, like name@example.com." name="email"></pds-input>
</DocCanvas>

**After a failed submit:** mark each failed field, render a `pds-alert` with `variant="danger"` above the form that lists the errors, and move focus to it. Give the alert `tabindex="-1"` so it can take focus, then call `focus()` on it. The forms guide shows the full example.

**Async validation:** set `loading` on the `pds-button` while you wait. A loading button sets `aria-busy="true"` on its inner `<button>` itself, so don't add `aria-busy` to it.

<DocCanvas
  mdxSource={{
    webComponent: `<pds-button loading>Checking availability…</pds-button>`,
    react: `
import { PdsButton } from '@pine-ds/react';

<PdsButton loading>Checking availability…</PdsButton>`
  }}>
  <pds-button loading>Checking availability…</pds-button>
</DocCanvas>

## Disabled vs Read-only

Choose the right pattern when a control should not accept input. `disabled` and `readonly` are not interchangeable: each has different keyboard, screen-reader, and form-submission behavior. `pds-input`, `pds-textarea` and `pds-datepicker` have `readonly`.

      <pds-table-cell>Screen readers</pds-table-cell>
      <pds-table-cell>Read it, as unavailable, when browsing the page</pds-table-cell>
      <pds-table-cell>Read it, as read-only</pds-table-cell>
    </pds-table-row>

> **Accessibility note:** People moving through the page with Tab never land on a disabled button, so they don't hear it or why it's disabled. If the action is important, keep the button enabled and show an error when it's pressed. Don't rely on `aria-disabled` on `pds-button`, which doesn't stop the click.

## Screen Reader Guidance

- Test with **VoiceOver** (macOS/iOS) and **NVDA** (Windows) as a smoke test
- Announce status changes via `aria-live` regions rather than moving focus unexpectedly
- Use `role="status"` for non-critical updates (equivalent to `aria-live="polite"`)
- Avoid `display: none` or `visibility: hidden` on elements that should be visually hidden but accessible. Use the `.visually-hidden` CSS pattern instead.

```css
.visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}
```

## Automated Testing

Pine runs axe-core against every component and every Storybook story in its own CI. That covers each component on its own, not how your app composes them. Run axe in your app's tests too (for example with `@axe-core/playwright`) to catch missing labels and broken ARIA wiring in your own markup.

Contributing to Pine? See <pds-link href="https://github.com/Kajabi/pine/blob/main/CONTRIBUTING.md#accessibility-gate" external>CONTRIBUTING.md § Accessibility gate</pds-link> for how Pine's CI checks run and how to run them locally.

## Testing Checklist

Use this checklist when reviewing a feature for accessibility:

- [ ] All interactive elements are reachable by `Tab` key
- [ ] Focus order matches visual reading order
- [ ] All inputs have visible, programmatically associated labels
- [ ] Error messages are associated with their inputs (`invalid` with `error-message` sets `aria-describedby` internally)
- [ ] Focus is trapped inside open modals
- [ ] Focus is restored when modals close
- [ ] Decorative images and icons have `aria-hidden="true"`
- [ ] Color is not the only way information is conveyed
- [ ] Text meets 4.5:1 contrast ratio (check with Storybook a11y panel or browser DevTools)
- [ ] Dynamic content updates are announced via `aria-live`
- [ ] Page works end-to-end using only a keyboard
- [ ] VoiceOver or NVDA smoke test passes for key user flows
