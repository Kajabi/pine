# Migration Guide

This guide covers how Pine communicates breaking changes, how to migrate between major versions, and how to stay current with releases.

For the full version history, see <pds-link href="../?path=/docs/resources-changelog--docs">Changelog</pds-link>.

---

## Deprecation Policy

Pine deprecates a public API before it removes it. <pds-link href="https://github.com/Kajabi/pine/blob/main/VERSIONING.md" external>VERSIONING.md</pds-link> has the full policy. In short:

1. **Deprecation notice** — the prop's JSDoc gets an `@deprecated` tag that names the replacement, and the component's generated readme marks the prop **[DEPRECATED]**. Pine doesn't log a console warning when a deprecated prop is used. For example, the <pds-link href="https://github.com/Kajabi/pine/blob/main/libs/core/src/components/pds-button/readme.md" external>`pds-button` readme</pds-link> marks the `icon` prop, which the `start` slot replaces.
2. **Deprecation period** — the deprecated API keeps working until a major release removes it.
3. **Removal** — in a major release.

Before each major upgrade, check the readmes of the components you use for **[DEPRECATED]** props.

## Breaking Change Format

The changelog marks breaking changes with `⚠️` and groups them under `### ⚠️ Breaking Changes`:

```
# 3.0.0 (2025-04-11)

### ⚠️  Breaking Changes

- ⚠️  **chip:** move value to slot (#364)
```

The changelog leaves out some commit types, such as `refactor`, even when the commit is a breaking change. That's why 4.0.0's changelog has no Breaking Changes section, although 4.0.0 removed `pds-chip`'s `large` prop. Version Migration Examples below covers that removal.

A major version bump (`2.x → 3.x`) always signals that breaking changes are present. Pine's policy is that minor and patch releases are non-breaking, but two 3.x minor releases removed APIs. Version Migration Examples below lists them too.

## Version Migration Examples

These are the props and events each major release removed or renamed, plus the two removals in 3.x minor releases.

### v3.x → v4.0.0

#### `pds-chip`: `large` removed

3.19.0 added `size` and deprecated `large`. 4.0.0 removed `large`. A chip that still sets it renders at the default `md` size, so use `size="lg"` instead.

```html
<!-- Before (3.x): large, removed in 4.0.0 -->
<pds-chip large>Design systems</pds-chip>

<!-- After (3.19.0 and later) -->
<pds-chip size="lg">Design systems</pds-chip>
```

In React:
```jsx
// Before (3.x): large, removed in 4.0.0
<PdsChip large>Design systems</PdsChip>

// After (3.19.0 and later)
<PdsChip size="lg">Design systems</PdsChip>
```

#### Removed in 3.x minor releases

If you're upgrading from an earlier 3.x release, check these too.

**3.10.0, `pds-popover`: `text` removed.** The popover no longer renders its own trigger button. Put your trigger in the `trigger` slot:

```html
<!-- Before (3.9.0 and earlier): text, removed in 3.10.0 -->
<pds-popover component-id="details" text="Details">
  <p>More about this item.</p>
</pds-popover>

<!-- After (3.10.0 and later) -->
<pds-popover component-id="details">
  <pds-button slot="trigger">Details</pds-button>
  <p>More about this item.</p>
</pds-popover>
```

**3.18.0, `pds-table`: `pdsTableSelect` removed.** Pine never emitted this event, so a listener for it never ran. Delete any `pdsTableSelect` listener, or `onPdsTableSelect` prop in React.

### v2.x → v3.0.0

#### `pds-chip`: `label` prop moved to the default slot

```html
<!-- Before (2.x): label, removed in 3.0.0 -->
<pds-chip label="Design systems"></pds-chip>

<!-- After (3.0.0 and later) -->
<pds-chip>Design systems</pds-chip>
```

**Why:** Moving the text from `label` to the default slot allows richer content inside chips and aligns with standard web component slot conventions.

#### `pds-checkbox`: `label-hidden` renamed to `hide-label`

```html
<!-- Before (2.x): label-hidden, removed in 3.0.0 -->
<pds-checkbox component-id="agree" label="Agree" label-hidden></pds-checkbox>

<!-- After (3.0.0 and later) -->
<pds-checkbox component-id="agree" label="Agree" hide-label></pds-checkbox>
```

In React:
```jsx
// Before (2.x): labelHidden, removed in 3.0.0
<PdsCheckbox componentId="agree" label="Agree" labelHidden />

// After (3.0.0 and later)
<PdsCheckbox componentId="agree" label="Agree" hideLabel />
```

#### `pds-box`: `padding-block` and `padding-inline` split into start and end

```html
<!-- Before (2.x): padding-block and padding-inline, removed in 3.0.0 -->
<pds-box padding-block="md" padding-inline="sm">Content</pds-box>

<!-- After (3.0.0 and later) -->
<pds-box padding-block-start="md" padding-block-end="md" padding-inline-start="sm" padding-inline-end="sm">Content</pds-box>
```

## Token Changes

Design token renames are tracked separately in the <pds-link href="https://github.com/Kajabi/ds-tokens/releases" external>ds-tokens releases</pds-link>.

When tokens are renamed, the old token is aliased to the new one during a deprecation period. After removal, any usage of the old token name resolves to `unset` or produces no value.

**How to catch stale token usage:** Search your styles for the old token names listed in the ds-tokens releases. Pine's <pds-link href="../?path=/docs/design-tokens-color-linting--docs">Color Linting</pds-link> rules check only Pine's own component styles, so they won't flag stale tokens in your app.

## Staying Current

**Subscribe to releases:**
- <pds-link href="https://github.com/Kajabi/pine/releases" external>Pine GitHub releases</pds-link> — watch for release notifications
- <pds-link href="https://github.com/Kajabi/pine-icons/releases" external>Pine Icons releases</pds-link>
- <pds-link href="https://github.com/Kajabi/ds-tokens/releases" external>Design Tokens releases</pds-link>

**Slack channels:**
- <pds-link href="https://kajabi.slack.com/archives/C046HHS5KTN" external>#design-system-discussion</pds-link> (Kajabi-internal) — design system conversation. GitHub releases are the complete record of what shipped.

**Before upgrading a major version:**
1. Read the full changelog section for the new major version, and its entry under Version Migration Examples above
2. Search your codebase for the props and attributes that version removes or renames
3. Run your app's lint and type checks after upgrading. With `@pine-ds/react` and `"moduleResolution": "node"` in your `tsconfig.json`, removed props show up as type errors. Other `moduleResolution` settings don't load the wrapper's prop types today, so rely on the search in step 2.
4. Run your app's test suites to catch visual or behavioral regressions
