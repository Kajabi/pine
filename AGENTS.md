# Pine Design System — Agent Instructions

## Project Overview

Stencil.js web component library in an Nx monorepo. Core components live in `libs/core/src/components/`.

- All components are prefixed with `pds-` (e.g., `pds-button`, `pds-table`)
- Each component may include: `*.tsx`, `*.scss`, `*.figma.ts`, `stories/`, `docs/`, `test/`, and auto-generated `readme.md`
- Composite components have nested subcomponent directories (e.g., `pds-table/pds-table-row/`)
- React wrappers are generated in `libs/react/`
- Generate new components: `npm run stencil.generate pds-[name]` — choose `*.scss Format`, then copy `stories/` and `docs/` from an existing component
- Design identity (tokens, color roles, per-component token map) is in `DESIGN.md`
- Building UI *with* Pine in another app rather than changing Pine? Use the agent skill in `skills/pine/` and the Pine MCP

## Component Development

- Use Stencil decorators: `@Component`, `@Prop`, `@State`, `@Event`, `@Listen`, `@Method`, `@Watch`
- Props should have JSDoc comments — these generate the auto-docs in `readme.md`
- Use `@Event()` with `EventEmitter` for custom events; prefix with `pds` (e.g., `pdsTableRowSelected`)
- Most components use Shadow DOM — style them with `:host` selectors and expose internals with `::part()`. A component without a shadow root (`shadow: false`, `scoped: true`, or no `shadow` option) must declare `@lightDom host-only` or `@lightDom renders-markup` in the JSDoc above `@Component`; a spec fails without it (see CONTRIBUTING.md § Generating New Components)
- Style with semantic `--pine-*` tokens: they switch for dark mode under `[data-theme="dark"]` and reach into shadow roots. For RTL use logical properties and `:dir(rtl)`. Don't add `:host-context()` — Firefox and Safari ignore it
- Don't remove or rename a public prop, event or method in place: mark it `@deprecated` in its JSDoc, keep it working, and remove it only in a major (see VERSIONING.md § Deprecation)
- `readme.md` is auto-generated by Stencil — do not edit manually

## Documentation

- JSDoc descriptions on `@Prop`, `@Event`, and `@Method` must use consistent terminology across components — review similar props/events on other components before writing new descriptions
- When adding a prop or event that exists in a similar form on another component, match the wording and phrasing of the existing description
- MDX docs live in the component's `docs/` folder and follow CONTRIBUTING.md § Writing component docs, because the Pine MCP parses the same file. Write each example as ``<DocCanvas mdxSource={{ react: `...`, webComponent: `...` }}>``: the MCP serves those two strings as the example code and strips `<Canvas>` and `<Story>`. Use `<Canvas of={stories.Default} />` only in the last section, `## Playground`
- Headings in a component's MDX are a contract, because agents read Pine's docs section by section and find sections by heading. Keep this order: `<StatusBadge>`; `# Title` and a one-paragraph summary; `## Guidelines` with exactly `### When to use`, `### When not to use` and `### Accessibility`, a blank line after `### Accessibility` and no other heading at any depth (give other guidance its own `##` section after Guidelines); `## Properties`; `## Examples` with one `###` per example; any other `##` sections; then `## Playground` last. `npm run docs.check` enforces the status badge, the title and summary, the Guidelines headings and blank line, `## Properties` after Guidelines and `## Playground` last
- Keep docs and comments consumer-neutral: describe Pine's behavior, not a particular app or framework that uses it
- Storybook stories in the component's `stories/` folder — export a default meta + named story exports

## Git Conventions

- Lefthook enforces commitlint, validate-branch-name, and lint-staged — never skip hooks
- Branch names: `{type}/{description}` — do NOT include ticket or issue numbers
- Accepted branch types: `chore`, `ci`, `docs`, `feat`, `fix`, `hotfix`, `perf`, `refactor`, `revert`, `style`, `test`
- Commit scope = component name (e.g., `feat(pds-table):`, `fix(pds-button):`), single line, no ticket numbers
- Commit type by file:
  - `feat(component):` — new props, events, methods, or component behavior in `*.tsx`
  - `fix(component):` — bug fixes in component code
  - `test(component):` — test files (`*.spec.tsx`, `*.e2e.ts`)
  - `docs(component):` — MDX docs, Storybook stories, and documentation updates
  - `style(component):` — SCSS/CSS-only changes
  - `refactor(component):` — code restructuring with no behavior change
  - `chore:` — tooling, config, dependencies
- PR titles: `type(scope): description` — always use the template at `.github/pull_request_template.md` for the PR body
- If your branch is behind `main`, rebase before pushing (`git rebase main`) — requires at least one approved review before merging
- See `CONTRIBUTING.md` for full contributor guidelines

## Testing

- Spec tests go in the component's `test/` folder (e.g., `pds-chip/test/pds-chip.spec.tsx`) using Stencil's `newSpecPage`
- E2E tests also in the component's `test/` folder using Stencil's `newE2EPage`
- Every new prop, event, or behavior needs corresponding test coverage
- E2E specs should assert `runAxe(page)` returns no violations (`libs/core/src/utils/test/axe.ts`); the themed Storybook gate covers `color-contrast` separately
- Never add entries to `libs/core/.storybook/a11y-baseline.json` by hand — regenerate it with `npm run test.a11y -- --update-baseline`. It should only shrink, except for new stories of a component that already has baselined violations (see CONTRIBUTING.md § Accessibility gate)

## Build & Test

- Build all: `npm run build.all` (`npx nx run-many --target=build`)
- Test all: `npm run test.all` (`npx nx run-many --target=test`)
- Accessibility gate: `npm run test.a11y` (axe over every story; needs `build.stencil` + `build.storybook` first — see CONTRIBUTING.md § Accessibility gate)
- Lint all: `npm run lint.all` (`npx nx run-many --target=lint`)
- Target core only: `npx nx run @pine-ds/core:build`, `npx nx run @pine-ds/core:test`
- Bundle size: build core, then `npm run size`; PR CI enforces the gzipped budgets (see CONTRIBUTING.md § Bundle size budgets)
- Public API: `npm run api.check`; after an intentional API change, run `npm run api.update` and commit the reports
- Docs: `npm run docs.check` (builds core first) checks each `DocCanvas` example's `pds-*` tags and `Pds*` components, `pds-icon` names and imported icons, web component attributes, and values of props limited to a fixed set of strings; each component's JSDoc descriptions, `@slot` and `@part` lines for the slots and parts it renders, and `@defaultValue` against the code default; each docs page's heading anchors, Storybook docs links and section size; and each component page's headings and status badge against CONTRIBUTING.md § Writing component docs. PR CI's `docs-check` job runs it (see CONTRIBUTING.md § Docs check)
- CI's `test-lint` job and the pre-push hook also run `npm run design.tokens -- --check` (DESIGN.md token block) and `npm run truncation.check` (truncated text needs a tooltip)
- After modifying `*.tsx`, rebuild to regenerate `components.d.ts` and `readme.md`
- Dev server: `npm run start` (Storybook at localhost:6006)
- Linting: ESLint (`@stencil-community/recommended` + `@typescript-eslint`), Prettier, and Stylelint

## Boundaries

- **Always:** follow existing component patterns, run lint and tests before committing, use conventional commits with component scope, match JSDoc terminology from similar components
- **Ask first:** adding new dependencies, creating files outside component directories, making breaking API changes (removing props/events), modifying CI/CD or build config
- **Never:** skip lefthook hooks, edit auto-generated files (`readme.md`, `components.d.ts`, `libs/*/etc/*.api.md` — refresh the API reports with `npm run api.update`) manually, commit secrets or `.env` files, modify `node_modules/` or `dist/`
